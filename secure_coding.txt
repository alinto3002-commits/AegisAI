SECTION 1: EXECUTIVE SECURE CODING PRINCIPLES
================================================================================
1. Defense in Depth:
   Never rely on a single layer of validation (e.g., client-side JS or single API
   gateway check). Enforce strict input validation, data encapsulation, database
   parameterization, and egress filtering at every layer of the architecture.

2. Principle of Least Privilege (PoLP):
   Applications and service accounts must execute with the absolute minimum
   operating system permissions and database privileges required. Disable administrative
   grants (e.g., root execution, DB superuser privileges).

3. Fail Securely (Fail Closed):
   When an exceptional condition or security failure occurs, the application must
   terminate the transaction, revert state changes, log the incident with security
   context, and return a neutral, generic error message to the client.

4. Secure by Default:
   All security controls, authentication gates, encryption standards, and CSRF/CORS
   protections must be enabled by default. Developers must explicitly justify and
   document any exceptions.

5. Never Trust User Input:
   Treat all incoming data—including URL query parameters, HTTP headers, cookies,
   file uploads, form bodies, and even internal RPC payloads—as untrusted and hostile.

6. Complete Mediation:
   Every access request to every secured resource must be checked against current
   authorization policies. Never cache access decisions across distinct HTTP requests.

SECTION 2: OWASP TOP 10 (2025 EDITION) TAXONOMY & THREAT MATRIX
================================================================================

[A01:2025] Broken Access Control (CWE-22, CWE-862, CWE-639, CWE-918)
- Threat: Attackers access unauthorized records (IDOR), traverse directory paths,
  forge server requests (SSRF), or perform admin operations without credentials.
- Defenses: Enforce server-side role-based access control (RBAC), canonicalize and
  verify filesystem paths, bind object lookups to authenticated user IDs, and
  block outbound HTTP connections to internal IP addresses (RFC 1918, 169.254.169.254).

[A02:2025] Security Misconfiguration (CWE-16, CWE-215, CWE-942)
- Threat: Debug mode enabled in production, wildcard CORS headers (`*`), default
  passwords, unnecessary endpoints exposed, unhardened framework headers.
- Defenses: Set `debug=False`, configure strict CORS origins, disable directory
  listing, remove test endpoints, enforce HSTS and Content-Security-Policy.

[A03:2025] Software Supply Chain Failures (CWE-1104, CWE-1395)
- Threat: Outdated dependencies with known CVEs (e.g. vulnerable Log4j or Jackson),
  unpinned package manifests, dependency confusion, or malicious package updates.
- Defenses: Pin exact versions with SHA-256 hashes, run automated vulnerability
  scanners (pip-audit, OWASP Dependency-Check, Snyk), and utilize private mirrors.

[A04:2025] Cryptographic Failures (CWE-327, CWE-328, CWE-329, CWE-338)
- Threat: Plaintext transmission of credentials, weak password hashes (MD5, SHA-1),
  symmetric encryption using ECB mode, or static/predictable initialization vectors.
- Defenses: Use TLS 1.3, store passwords with Argon2id or bcrypt (cost >= 12),
  encrypt sensitive data at rest with AES-256-GCM using unique 96-bit nonces.

[A05:2025] Injection (CWE-89, CWE-78, CWE-611, CWE-90, CWE-94)
- Threat: SQL, OS command, LDAP, or XML injection where attacker input alters
  the query structure or executes arbitrary system binaries.
- Defenses: Parameterized queries (PreparedStatement, ORM parameters), avoid `shell=True`
  and `Runtime.exec`, disable external entity resolution (XXE) in XML parsers.

[A06:2025] Insecure Design (CWE-1059, CWE-307)
- Threat: Flaws in architectural design such as missing rate limits on login/reset
  endpoints, lack of business logic constraints, and unconstrained resource consumption.
- Defenses: Threat modeling, rate limiting (token bucket / Leaky Bucket), CAPTCHA
  on credential endpoints, strict pagination, and schema validation.

[A07:2025] Authentication Failures (CWE-798, CWE-345, CWE-347)
- Threat: Hardcoded API keys, tokens, or passwords; weak session IDs; insecure JWT
  verification; lack of multi-factor authentication for sensitive actions.
- Defenses: Externalize secrets to environment variables or secret vaults (HashiCorp
  Vault, AWS Secrets Manager), enforce JWT signature validation and algorithm whitelists.

[A08:2025] Software or Data Integrity Failures (CWE-502, CWE-94)
- Threat: Deserializing untrusted byte streams (Python pickle, Java ObjectInputStream)
  leading to arbitrary remote code execution (RCE) via gadget chains.
- Defenses: Restrict serialization to JSON/Protocol Buffers with explicit schema
  validation; use ObjectInputFilter in Java; avoid `pickle.loads` on external data.

[A09:2025] Security Logging and Alerting Failures (CWE-532, CWE-117)
- Threat: Leakage of secrets, passwords, or PII into system log files; lack of
  audit trails for high-risk actions; log injection via unescaped newlines.
- Defenses: Sanitize log messages (strip CRLF characters), mask sensitive credentials,
  maintain immutable audit trails for auth events and financial transactions.

[A10:2025] Mishandling of Exceptional Conditions (CWE-755, CWE-390, CWE-404)
- Threat: Suppressing exceptions with bare `except: pass` or empty `catch (Exception e) {}`
  blocks, masking authorization or database crashes, leaving system in inconsistent state.
- Defenses: Catch specific exception classes, log diagnostic context with stack traces,
  clean up resources via `finally` or `try-with-resources`, return clean HTTP errors.

4.1 SQL Injection Prevention (CWE-89)
--------------------------------------
VULNERABLE:
  cursor.execute(f"SELECT * FROM users WHERE username = '{username}'")
  cursor.execute("SELECT * FROM items WHERE category = '%s'" % category)

SECURE:
  # Using SQLite3 / DB-API 2.0 Parameterization
  cursor.execute("SELECT * FROM users WHERE username = ? AND is_active = 1", (username,))
  
  # Using SQLAlchemy 2.0 Parameterized ORM Queries
  stmt = select(User).where(User.username == username, User.is_active.is_(True))
  result = session.execute(stmt).scalars().first()

4.2 Path Traversal & ZipSlip File Security (CWE-22)
---------------------------------------------------
VULNERABLE:
  file_path = f"/var/data/uploads/{filename}"
  with open(file_path, "rb") as f:
      return f.read()

SECURE:
  from pathlib import Path
  from fastapi import HTTPException
  
  BASE_STORAGE = Path("/var/data/uploads").resolve()
  target = (BASE_STORAGE / filename).resolve()
  
  if not target.is_relative_to(BASE_STORAGE) or not target.exists():
      raise HTTPException(status_code=403, detail="Access denied: invalid file path")
  return target.read_bytes()

4.6 SSRF Egress Defense (CWE-918)
---------------------------------
VULNERABLE:
  import requests
  return requests.get(user_supplied_url).text

SECURE:
  import ipaddress, socket, requests
  from urllib.parse import urlparse
  
  def safe_fetch(url: str) -> str:
      parsed = urlparse(url)
      if parsed.scheme not in ("http", "https"):
          raise ValueError("Scheme must be HTTP/HTTPS")
      ip = ipaddress.ip_address(socket.gethostbyname(parsed.hostname))
      if ip.is_private or ip.is_loopback or ip.is_link_local:
          raise SecurityError("Access to internal networks is forbidden")
      return requests.get(url, timeout=3, allow_redirects=False).text

SECURE:

  }

SECTION 6: CRYPTOGRAPHIC IMPLEMENTATION STANDARDS
================================================================================
1. Symmetric Ciphers:
   - Primary: AES-256-GCM (Galois/Counter Mode).
   - Tag Length: 128 bits (16 bytes).
   - IV / Nonce: Exactly 96 bits (12 bytes), generated via cryptographic PRNG.
   - Forbid: AES-ECB, DES, 3DES, Blowfish, RC4.

2. Asymmetric Cryptography:
   - RSA: Minimum 2048-bit keys (3072-bit recommended for 2025+). OAEP padding for encryption.
   - Elliptic Curve: Ed25519 (signatures), Curve25519 / X25519 (key exchange), ECDSA P-256.

3. Transport Layer Security:
   - Minimum: TLS 1.2 (TLS 1.3 preferred).
   - Disable SSLv2, SSLv3, TLS 1.0, TLS 1.1.
   - Enforce HSTS (Strict-Transport-Security: max-age=31536000; includeSubDomains).

SECTION 7: CODE SMELLS, DESIGN ANTI-PATTERNS & REFACTORING RULES
================================================================================
1. Cyclomatic Complexity Limit:
   - Maximum 10 per method/function.
   - Refactor via Extract Method, Strategy Pattern, and early return Guard Clauses.

2. God Class / Monolithic Controller Anti-Pattern:
   - Threshold: Classes exceeding 300 lines or > 15 public methods.
   - Refactor by splitting into Single Responsibility Principle (SRP) service delegates.

3. Deep Nesting Anti-Pattern:
   - Threshold: Nesting depth > 3 levels.
   - Refactor by inverting conditional logic and failing fast with early returns.

4. Long Parameter List:
   - Threshold: > 4 parameters.
   - Refactor into Command DTOs, Java Records, or Pydantic models.
